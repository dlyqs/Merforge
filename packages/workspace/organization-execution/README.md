# @deepseek-ai/dsh-organization-execution

Owns local Run/Session preparation and API and Codex execution intervals described in the [execution protocol](../../../../docs/organization-execution.md). The service definition and implementation are `OrganizationExecution`; Electron's fixed execution operation and the private Desktop Host IPC controller consume `open`, `executeConfigured` and `report`. Organization SQLite remains the sole business authority.

Desktop loads the service with a dedicated `root`. An isolated Cordis context owns a persistent JSONL provider in the `organization-execution` namespace. Preparation registers no Agent or tool. The internal `execute` method builds a separate temporary Agent/Session registry using the standard loop, tool registry and filesystem implementation. It registers its application-owned model adapter, selected `read_file` / `write_file` consumers, and a `request_human` consumer backed by the scoped user-questions service. The API composition omits personal presets, prompts, memories, background jobs, terminals and subprocess providers. The Codex path consumes the Host subprocess provider separately and never mounts this API composition. Personal Session and Agent admission, persistence, and consumers of `assertPersonalSessionId` reject execution IDs. Creating a personal child with an organization parent is also refused.

The atomic `organization_execution` domain reserves server/account/Run and operation identities before JSONL creation. A required `organization/execution-binding` event retains the immutable Run, original context Session, exact authorized task, explicit model selection, materials and employee messages. The original two-event `organization-context` log is unchanged. The shared authority receives only the input digest; paths, credentials and full conversations are not uploaded. Changed inputs require a new explicit execution grant and Run.

`open` accepts a strict selector and a private native recheck callback. Native authentication supplies account identity, current execution eligibility and task projection; Renderer cannot choose a Session ID or provide authority. Startup nonce, request and authorization IDs, native generation, owning window and deadlines correlate each exchange. Cancellation and disposal abort pending authorization. Persistence can repair an interrupted matching prefix; mismatched data is refused. Ready state follows flush and independent read, and delivery follows another online recheck.

Cold start verifies reserved/ready/executing/stopped bindings, operation references, orphan logs and the ordering and Run ownership of durable action evidence. An interrupted or stopped binding refuses another execution unless the employee explicitly requests reconciliation and continuation. The `./invariant` companion compares the binding domain and separate JSONL store; Loader tests execute it and exercise persisted corruption. The service never treats a local record or receipt as current execution permission.

## Backend scheduling metadata

SQLite authority reads may contain an explicit Codex backend and native policy. Fixed HTTPS/native/private IPC transport carries those validated fields without credentials or native home paths. Shared metadata is excluded when deriving signed command selectors. API Run preparation and execution retain their existing model permits.

`executeConfigured` routes explicitly selected native Runs to the Codex consumer before selecting an API model or starting a loop. Native scheduling qualification alone neither starts work nor grants access to native tools; employee start remains explicit.

## Internal execution consumer

`executionLimits` is an optional validated Config field containing `maxActions`, `maxSteps`, `maxDurationMs`, `maxBytes` and `recheckMs`. Omission disables `execute`. Desktop supplies finite ceilings and explicit local text model routes. Execution also requires explicit local `inputs.execution` directory and action/step/duration limits, covered by the original configuration digest. Old prepared inputs cannot gain execution permission. The application resolves the adapter from `models`; each entry fixes the model, exact HTTPS /v1 endpoint, credential reference, output/context limits and idle timeout. The organization authority supplies its independent `executionModels` allowlist on every read. The employee selection must match both. Renderer has no callback or adapter parameter.

`action-guard.ts` reserves a new charged permission per actual model attempt, including retries. It serializes actions, flushes local `reserved` and `issued` evidence, rechecks native identity, lease, exact revision, capability and permit expiry before dispatch, and writes observed settlement before reporting it. Lost acknowledgements halt new work; unknown effects are never replayed. The model adapter's known failure result is recorded separately from an unknown transport or consumer outcome. A completed Run is not an employee submission or task acceptance.

`resources.ts` admits only regular UTF-8 files within the canonical selected directory, rejects traversal, links and Windows alternate path forms, and rechecks the target before the filesystem call. Process-local directory locks reject overlapping roots and are held through cancellation drain. These trusted consumers do not defend against an adversarial OS owner swapping filesystem ancestors concurrently. The API consumer executes no model-controlled code or shell; its shell capability is refused because the existing process sandboxes do not promise restricted reads and network access.

`runtime.ts` mounts the real loop and persistence in a private context, records original task/materials/messages through the normal durable input path, enforces step/action/time/byte limits, checks online authority during in-flight work, and awaits adapter and log teardown. Model output is currently buffered within the byte ceiling before delivery. The required `organization/execution-action` event remains local. The persistence catalog recognizes it; older readers refuse it.

## Model Experience

- Model-visible behavior: preparation sends no request. Internal execution logs the exact task and explicit employee inputs before sending them; selected file tools expose only relative paths and bounded content.
- Token usage: preparation uses none. Each actual execution request or retry requires its own charged permission; step, duration and output-byte ceilings bound the interval.
- KV-cache effects: the isolated Run retains its own logged model history; it never reuses a personal Session or private Bot context.

## Known Limitations and Deferred Work

Native file-change callbacks without a complete comparable proposal are cancelled after Inbox recording; an old file-change decision cannot approve a new item. Native command decisions can answer one identical fresh callback only after explicit continuation. Live native account/model behavior, Windows and visible multi-device acceptance remain unverified.

Desktop provides an explicit start form, Run summaries and pause/cancel controls. Native execution channels use a separate identity lifetime from content generations; stop acknowledgements wait for the owned Host interval. Durable HumanRequest and explicit same-Run recovery are implemented. Organization artifacts, formal submissions, issuer acceptance and native target integration are implemented by the separate organization authority and Desktop consumers. A prepared Run cannot resume automatically after server epoch replacement. Full logs remain local to the employee.

`model.ts` constructs a fresh DeepSeek text adapter with no personal provider settings, attachments or request-extension plugins. Local credentials resolve only for an exact configured destination. Immediately before each Messages HTTP request, the adapter reads current authority, checks the model policy and consumes one reserved model action; it refuses internal reuse of the same action. The outer retry loop must reserve a fresh permission. Credentials and responses are not logged into shared organization records.

`report` reads bounded plain-text instructions, assistant messages and tool results from the private JSONL. Native report IPC checks exact task access before reading and again before delivery, and the service matches the original account/server binding. Truncated reports retain only the tail within the complete JSON byte limit. Reports never enter the organization HTTP response or personal Session APIs.

## Human requests and historical evidence

The isolated `user-questions/request` answerer persists a designated organization question and ends the interval in `waiting-human`. It delegates unrelated Agents with `next()`. Questions survive Host disposal. Answers and file approvals use separate participant commands, and neither automatically resumes an Agent. Explicit continuation records the authoritative answers through `user/message` before they become model-visible. `inputs.requireWriteApproval`, when selected, requires a one-use approval for each exact write request without changing the original capabilities.

`report` includes local tool parameters, recovery classifications, the original employee inputs and a bounded directory fingerprint. The runtime compares that fingerprint again under its directory lock. `recovery.ts` reads actual files to check pending write evidence; missing or unobservable results stay unknown. An issued write may be confirmed by matching bytes without repeating the write. A reserved-only journal supports a charged `not-issued` historical settlement. `reconcile` only reports retained evidence and cannot run a model; it works after ownership expiry while the original employee/device retains current task access. `execute` with explicit `resume` additionally checks current qualification, pending requests and remaining budget.

Directory inspection includes regular file bytes and path metadata within `executionLimits.maxBytes`. Oversized directories, links and special files fail closed. Recovery uses the same trusted-OS-owner assumption as the file consumers. Replaced server/fencing epochs and expired grants require explicit fresh delegation/claim and a new Run after historical reconciliation and cancellation; the old Run never gains new ownership. New Runs do not silently import or replay prior conversations.

## Composition verification

Desktop `organization-execution.spec.ts` exercises the real Loader, native HTTPS authorization, SQLite, private JSONL, file tools, human waiting, Host reopening, rework and two-child target delivery. Its only execution substitute is a deterministic model adapter. The shared fixture supplies the published Node/Electron private-IPC smoke and an opt-in real-model CSV test. The [acceptance guide](../../../../docs/organization-execution-acceptance.md) records commands, coverage and user-owned release/platform checks; scripted responses do not certify model routing or OS safeStorage. No new Session event or invariant relation is introduced by these test lanes.

## Native Codex execution

`executeConfigured` requires inputs.backend to match the immutable Run backend, exactly `codex-turn` capability and matching model/turn/time limits. The optional `codex` Config contains all native runtime waits and byte/queue bounds; its omission disables native execution. Desktop supplies those limits and the subprocess provider. The organization server separately requires an opt-in `executionCodex` policy. No API credential or endpoint is used.

`codex.ts` locks the explicitly selected canonical working directory without scanning its files. It uses the employee's native Codex authentication and configuration; it neither copies the native home nor supplies other Merforge Session/Bot history. Each Run reserves its own `organization-execution:` Session, records thread preparation before creation, binds one persistent thread, and records input identity, turn/start intent, receipt, observed items and authoritative terminal. The required `organization/execution-native` event is recognized by current readers; Session envelope and storage-domain versions stay unchanged. Native context, shell/file/MCP/subagent actions and quality remain Codex-owned.

One scheduling action is charged per dispatched native turn. `nativeActive` is an independently fresh authority check of exact-task access, policy, prerequisites, delegation, device and lease for an already running turn; it remains true after the final turn budget is consumed, but not after authority or time loss. The consumer polls it during preparation and execution. Native tools do not consume Harness action permits. Abort stops and awaits the owned process and journal writes. A durable terminal survives independent cleanup failure, retained as a separate local diagnostic. Native status does not submit or accept an artifact.

Human questions and approvals persist in the designated organization Inbox before the native callback is cancelled and the process drains. Replies do not start work. Explicit continuation creates a new turn on the same native thread after current qualification checks. An approved/denied command with identical semantic request fields and cwd can answer one fresh callback after explicit continuation; its consumed decision is durable and checked again online before replying. Changed requests require a new decision. File-change approvals without a complete comparable proposal are cancelled and must be requested again; a previous item identity never grants a new file-change permission.

Native recovery uses a digest of the reviewed private journal, not a file-tree fingerprint. A confirmed receipt permits an exact thread/turn history read and durable terminal settlement; missing receipts, in-progress native turns and unconfirmed thread creation remain unknown and are never resent or replaced. Reconciliation does not dispatch. Current owner and exact-task access guard reports before read and delivery. Pure presenters expose known text/tool fields and fixed statuses; protocol identifiers, native account information and stderr do not become shared UI contents. Full history stays in the employee's isolated log and is refused by personal search, fork and upload APIs.

Real native login/model behavior, Windows and visible/multiple-device acceptance remain user-owned. `apps/desktop-host/tests/organization-codex-built-smoke.mjs` verifies published private IPC/HTTPS/SQLite/JSONL consumption with an offline native peer under Node and Electron Node mode, after a Desktop build.
