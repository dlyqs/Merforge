# @deepseek-ai/dsh-client-ui-organization

Project and Inbox content refreshes preserve the current ordinary conversation reference and the last authorized sidebar catalog while replacement queries run. Account/organization changes and offline state release the reference; reconnecting can reopen the selected history without replaying a prompt. Newly attached conversations enter the native catalog before execution starts.

## Summary

Adds organization settings and a personal/organization switch to Desktop. The [organization design](../../../docs/organization-foundation.md) owns the product behavior. A typed native preload capability supplies safe snapshots and fixed operations; renderer code never receives bearer tokens or private certificate keys.

## Use this package

The task workspace and inline conversation plans use the shared TaskMap, TaskDetail and TaskStages primitives with personal mode. Task identity, close control and section navigation remain fixed above the independently scrolling body. Overview, Assignment, Execution, Review and Delivery are separate sections whose unfinished inputs survive navigation. Assignment groups version/member review and employee acceptance. Execution leads with the ordinary task conversation and offers isolated Runs in an advanced disclosure. Ordinary Agent and manual work can upload and submit results without a Run. Upload and formal submission have separate confirmations; rejection has a reason/requirements form. Technical identifiers, history and target evidence use secondary disclosures. Dependencies below the canvas use only readable task projections.

Conversation task details retain the selected section and unfinished inputs while authority refreshes. Batch assignment is a disclosure inside Assignment; each leaf keeps its assignee and result visible, with scope and acceptance details expandable. Run transcripts scroll inside a bounded viewer. Formal submission is blocked by unresolved actions or pending human requests; expired or cancelled requests do not remain blockers.

Native model setup actions open Settings → Models → Codex through the shell-owned settingsNavigation service. Opening setup does not select a model, save a Bot, create a Session, or start an organization Run. Pushed catalog invalidations refresh availability; callers retain their current draft and explicitly choose the model and effort after setup.


The shipped Web bundle loads the plugin. Settings show compact account and local-service summaries that open a centered organization workspace. The workspace groups account, projects, members, reporting hierarchy and local-service operations; each editing task replaces the overview with a focused form. The sidebar keeps the shared account avatar and the Tasks, Projects, Bots and Recent entries; setup forms use centered dialogs. Dialogs retain keyboard focus and return it to the entry on dismissal; pending operations prevent dismissal. The workspace provides local service configuration, certificate comparison, initialization/recovery, invitation registration, login/logout, organization selection, member management and explicit project grants. Service maintenance opens native backup/restore directory dialogs. Product copy uses the `organization` typed locale in Chinese and English. In personal mode the sidebar reuses `personal.manager` for the original Project/Bot/Session navigation; it does not copy or transfer personal records.

New projects open their task destination with the creator's atomic read/write grant. Project and task access controls retain their current authority checks. Empty task lists direct the user to describe a goal in a project conversation; there is no manual task-creation workbench. Model proposals create shared unapproved plans through the sole WorkGraph writer. The task destination reads authorized pages and displays the shared canvas with assignment, execution and delivery controls in its right detail area. Existing-plan edits retain operation identities and require revalidation after generation changes. Task access is supplied by assignment; independent task grant administration is removed.

Native generations hide expired task pages, grants and context results immediately. Existing-plan drafts survive transient failures within the workspace but require online revalidation after a generation change; new unsaved drafts remain available to the same identity while online. Closing the task workspace or switching identity drops drafts. The native context action shows only the original persisted task snapshot. A separate execution panel requires explicit model, endpoint, local directory, file capabilities and limits before granting and starting a Run. It shows current-authority Run history, budgets and stop controls, with an employee-only local transcript reader.

The task panel checks issuer authority and reporting eligibility automatically and requires version confirmation before assignment. Assignment supplies employee project and selected-task read/write access, and the Inbox synchronizer materializes one private task conversation. The employee explicitly accepts or rejects. Accepted tasks wait for an employee prompt to the ordinary Agent or manual execution; no device registration, preparation capability form or claim action remains. Dispatchers may revoke the assignment. Historical outputs and approval records remain visible under current task access.

Inbox and project details both open the original read-only context; revision differences are shown without overwriting JSONL. Assignment results are generation-scoped. Legal form drafts survive transient refreshes within the same identity; a version conflict clears confirmation and re-reads. Switching account/organization remounts the workspace and clears drafts and content.

## Model Experience

Preparation uses no model calls, prompt tokens or KV-cache changes. Explicit execution sends the logged task and employee instructions to an isolated text model, with one charged permission per attempt and no personal Session cache reuse. Opening a context can persist the two organization ownership/task-snapshot events through the private Host; presentation itself adds no Session event. Human answers enter model history only on explicit continuation.

## Known Limitations and Deferred Work

Visible Desktop acceptance and three-computer Wi-Fi validation remain user-owned; see the [acceptance script](../../../docs/organization-foundation-acceptance.md). Advanced authorization still requires a supplied project ID when the administrator lacks a read grant. Password and invitation forms do not provide account discovery or email delivery.

The [WorkGraph acceptance script](../../../docs/organization-workgraph-acceptance.md) covers task permissions and pre-execution contexts. GUI creation is single-task; existing complex plans expose their authorized tree and text editing, with no structural graph editor. Member selectors use only the authorized native directory and current membership. Accounts without directory access retain an advanced member-ID input; this UI does not expand member-directory permissions. Drafts are not persisted across workspace closure or application restart. Assignment, acceptance, optional bounded execution, human requests and explicit local recovery are implemented; formal submission, original-issuer acceptance and versioned rework are implemented; target verification and parent integration use the existing native verification controls.

No invariant companion is published: this plugin renders the native owner's snapshot and has no second authority. The composition test checks registration/disposal without mounting a page; native integration tests own isolation and race coverage.

The circular avatar occupies `sidebar.account` at the primary rail top. It opens a centered account dialog listing Personal and available organizations, with the active workspace marked from native state. Failed selections remain open. Account management opens the connection workspace. Keyboard focus remains inside the dialog and returns to the avatar on dismissal; motion respects reduced-motion preferences.

Organization setup accepts an address without a scheme; the native connection trims it and adds HTTPS before probing, and the form shows the normalized address. Connection and certificate verification appear on the account overview before login or invitation registration. Invitation registration signs in automatically. Password fields offer an accessible visibility toggle; creation, change and recovery require matching confirmation and at least eight characters. Operation feedback appears once, clears on editing or navigation, can be dismissed, and expires after six seconds; connection status and pending-write reconciliation remain visible.

Task details and the Run panel show execution questions, designated handlers, decision states and answers. File approval is separate from work information and requires reading the local tool parameters first. Recovery shows per-action reasons, the selected directory, its fingerprint and the remaining budget. Employee confirmation precedes either historical reconciliation or continuation. Unknown effects and stale baselines block continuation; expired ownership requires fresh explicit grant/claim and a new Run after cancelling the old one. None of these controls represents formal task acceptance.

`DeliveryPanel` accepts a text result, commit record or URL, optional additional notes and optional file attachments selected from the left plus button. File sizes and limits use MB/GB. One employee confirmation publishes selected attachments and submits their receipt ids for issuer review; partial upload retries retain stable operations and previously published files. Standard file selection transfers only selected bytes; it never scans a directory or follows shared path metadata. Test reports render as escaped text, and downloads use a local `application/octet-stream` Blob without executing content. Git packages are explicitly selected JSON evidence in the documented format; automatic repository packaging and target application are not implemented in this phase. Task details show the immutable submission and downloadable evidence for the original issuer. Same-account permission refreshes hide stale content while preserving the mounted upload operation; identity changes clear sharing drafts. Visible Desktop acceptance remains user-owned.

`AcceptanceReview` requires the original issuer to confirm the displayed submission and evidence before accepting or rejecting. Rejection requires a reason and new requirements and explains whole-plan qualification invalidation. Task history shows accepted, rework, superseded and blocked outcomes separately; acceptance explicitly leaves target verification and final delivery outstanding. Durable employee task notifications retain a rework notice until the newer task version is approved, after which assignment and employee acceptance controls apply.

`IntegrationPanel` separates prerequisite readiness, accepted required outputs, target observations and final delivery. It lists only the complete currently readable submission/hash set, requests a native directory dialog for verification and requires an explicit issuer checkbox before final confirmation. Native generations hide stale content. Actual target reads, permission and confirmation rules stay in Electron and the organization authority; the UI never supplies hashes as verification evidence. Visible acceptance remains user-owned.

## Organization navigation and hierarchy

Switching to an organization fills the existing Projects, Bots and Recent browsers with that identity's authorized organization data. The global plus action directly creates an account-private conversation without a project; these conversations appear in Recent. Project-row creation retains its explicit project and optional Bot. Every enabled organization member can create a project from the Projects header; creation grants that member read/write access. Recent rows reopen their original private conversation. Bots are account-private, project-scoped configurations with a name, instructions and an ordinary API/Codex model selection. Their create/edit form reads the same model directory as personal conversations and saves through fixed native actions. A new conversation uses the Bot default; an explicit conversation selection takes precedence across reopen. Navigation reads every authorized project page independently of workspace search. A failed private catalog preserves the project rows and other successful catalogs; Recent reads conversations without a project independently of project enumeration. Identity changes clear conversation and task selections and restore the personal navigation registrations.

The Tasks browser uses the shared task-row presentation and lists readable roots. Selecting a row opens the same task canvas used by personal plans. Selecting a canvas node opens its scope, acceptance and current version in the right detail area, alongside assignment, editing and the action to execute in a common conversation. All pages of the selected authorized plan are read before drawing it; unreadable ancestors remain absent. To distribute work, choose a node, select a named eligible member, review the exact task version and confirm approval. Assignment supplies employee project and selected-task read/write access atomically. Ordinary members may assign to themselves and direct reports; administrators may assign any member, while project/task permissions remain mandatory.

The organization workspace's Hierarchy tab draws current reporting relationships. Administrators select a member, choose their direct supervisor (or a root), and explicitly save using the displayed version. The server refuses cycles and cross-organization supervisors and recomputes existing assignment eligibility. Chart visibility confers no project/task permission.

The project-row menu confirms shared deletion for the original creator and installation-local removal for other participants. Shared deletion removes participant copies after their next online refresh; local removal preserves the shared project and every other installation. Both remove the selected installation's private project conversations and Bots. Removal identifiers survive restart and prevent automatic assignment imports from recreating the project. Background navigation refreshes render no status row, so refresh text does not move the navigation or task content. Member management appears only for organization administrators. The authority restricts employee charts to all descendants, colleagues sharing their immediate supervisor and the ancestor reporting chain; administrators receive the full chart, including disabled members.

The native organization adapters retain online permissions, identity generations and account-owned private history; sharing presentation never grants personal records organization ownership.

## Project information and task actions

Project row menus contain View project and Delete (or installation-local removal for participants). View project replaces the main conversation area with current project information. The creator may edit name, background, summary and goal; other readers see read-only fields. Both project creation entries save this context. The task list below the information opens an exact node in the task destination.

The organization management dialog has no pending-work tab. Pending assignment, execution-question, tool-approval and delivery requests appear in the task view; task-map nodes and plan rows distinguish items needing the current member's attention. Selected assignment details show immutable delivery evidence and original-issuer acceptance or rework controls, including history after a decision. Native inbox records remain the durable source for these facts and assignment conversation synchronization.

Primary Projects and Bots navigation selects the first displayed group's first conversation; Recent selects its first conversation. These destinations reuse loaded catalogs; refreshes enumerate projects once and read their private catalogs concurrently. The prior attached conversation remains visible until its successor is ready. A resident account entry shows loading when no reference is available, without rendering the unsaved composer between selections. Empty groups show an actionable new-conversation entry with the requested project and Bot retained. Creating from that entry opens the standard composer. No prompt or task action is sent by navigation.

The task map shows the latest shared task background to every authorized node reader. The original creator edits it independently of task revisions and handles durable whole-tree requests; assigned members can request read-only access and see pending, approved or rejected results. The map marks the current member's assigned nodes after approval. Sharing controls remain available in the map's fullscreen view, and task navigation marks creator requests awaiting review. All sharing content follows the current native identity generation.

Delivery accepts a text result, commit record or URL with optional file attachments selected from the composer plus button. Attachment sizes and limits use MB/GB. Selected files remain visible after the file input resets; attachment count, size and missing-description errors explain submission blocking. A result summary and explicit confirmation are required before submission. The task detail and delivery form remain mounted but hidden during native refreshes, so an upload can continue into formal submission without losing its draft or receipts. Confirmation publishes the selected attachments before submitting their receipt ids; text-only submissions and issuer review do not require files. Pending issuer Inbox submissions create account-private review conversations keyed by submission id, with the submitted summary, shared attachment descriptions and task selected; opening them never starts a model. The execution section reads the employee's authorized task conversation, checks the exact task revision and displays dispatched turn state separately from delivery approval.
