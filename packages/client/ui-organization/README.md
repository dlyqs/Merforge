# @deepseek-ai/dsh-client-ui-organization

Project and Inbox content refreshes preserve the current ordinary conversation reference and the last authorized sidebar catalog while replacement queries run. Account/organization changes and offline state release the reference; reconnecting can reopen the selected history without replaying a prompt. Newly attached conversations enter the native catalog before execution starts.

## Summary

Adds organization settings and a personal/organization switch to Desktop. The [organization design](../../../docs/organization-foundation.md) owns the product behavior. A typed native preload capability supplies safe snapshots and fixed operations; renderer code never receives bearer tokens or private certificate keys.

## Use this package

Native model setup actions open Settings → Models → Codex through the shell-owned settingsNavigation service. Opening setup does not select a model, save a Bot, create a Session, or start an organization Run. Pushed catalog invalidations refresh availability; callers retain their current draft and explicitly choose the model and effort after setup.


The shipped Web bundle loads the plugin. Settings show compact account and local-service summaries that open a centered organization workspace. The workspace groups account, projects, members, reporting hierarchy and local-service operations; each editing task replaces the overview with a focused form. The sidebar keeps the shared account avatar and the Tasks, Projects, Bots and Recent entries; setup forms use centered dialogs. Dialogs retain keyboard focus and return it to the entry on dismissal; pending operations prevent dismissal. The workspace provides local service configuration, certificate comparison, initialization/recovery, invitation registration, login/logout, organization selection, member management and explicit project grants. Service maintenance opens native backup/restore directory dialogs. Product copy uses the `organization` typed locale in Chinese and English. In personal mode the sidebar reuses `personal.manager` for the original Project/Bot/Session navigation; it does not copy or transfer personal records.

New projects open their task destination with the creator's atomic read/write grant. Project and task access controls retain their current authority checks. Empty task lists direct the user to describe a goal in a project conversation; there is no manual task-creation workbench. Model proposals create shared unapproved plans through the sole WorkGraph writer. The task destination reads authorized pages and displays the shared canvas with assignment, execution and delivery controls in its right detail area. Existing-plan edits retain operation identities and require revalidation after generation changes. Task access is supplied by assignment; independent task grant administration is removed.

Native generations hide expired task pages, grants and context results immediately. Existing-plan drafts survive transient failures within the workspace but require online revalidation after a generation change; new unsaved drafts remain available to the same identity while online. Closing the task workspace or switching identity drops drafts. The native context action shows only the original persisted task snapshot. A separate execution panel requires explicit model, endpoint, local directory, file capabilities and limits before granting and starting a Run. It shows current-authority Run history, budgets and stop controls, with an employee-only local transcript reader.

The task panel reviews issuer authority and reporting eligibility automatically and requires explicit version confirmation before assignment. Assignment atomically grants the assignee project read/write and selected-task read/edit access. Ordinary leaders can assign their direct reports without an administrator permission step; other task permissions stay unchanged. The employee sees the same authority-owned project, and the native Inbox synchronizer materializes one private task conversation per assignment when online. Persistent pending/processed inbox entries support explicit acceptance/rejection and independent read acknowledgement. Accepted employees separately register a native device, choose preparation capabilities, duration and budget, grant delegation, then claim explicitly. Dispatchers can read current preparation metadata. Status text never calls a held lease running or complete. Revocation, expiry, version loss and stopped renewal remain distinct.

Inbox and project details both open the original read-only context; revision differences are shown without overwriting JSONL. Assignment results are generation-scoped. Legal form drafts survive transient refreshes within the same identity; a version conflict clears confirmation and re-reads. Switching account/organization remounts the workspace and clears drafts and content.

## Model Experience

Preparation uses no model calls, prompt tokens or KV-cache changes. Explicit execution sends the logged task and employee instructions to an isolated text model, with one charged permission per attempt and no personal Session cache reuse. Opening a context can persist the two organization ownership/task-snapshot events through the private Host; presentation itself adds no Session event. Human answers enter model history only on explicit continuation.

## Known Limitations and Deferred Work

Visible Desktop acceptance and three-computer Wi-Fi validation remain user-owned; see the [acceptance script](../../../docs/organization-foundation-acceptance.md). Advanced authorization still requires a supplied project ID when the administrator lacks a read grant. Password and invitation forms do not provide account discovery or email delivery.

The [WorkGraph acceptance script](../../../docs/organization-workgraph-acceptance.md) covers task permissions and pre-execution contexts. GUI creation is single-task; existing complex plans expose their authorized tree and text editing, with no structural graph editor. Member selectors use only the authorized native directory and current membership. Accounts without directory access retain an advanced member-ID input; this UI does not expand member-directory permissions. Drafts are not persisted across workspace closure or application restart. Approval, preparation, bounded execution, human requests and explicit local recovery are implemented; formal submission, original-issuer acceptance and versioned rework are implemented; target verification and parent integration use the existing native verification controls.

No invariant companion is published: this plugin renders the native owner's snapshot and has no second authority. The composition test checks registration/disposal without mounting a page; native integration tests own isolation and race coverage.

The circular avatar occupies `sidebar.account` at the primary rail top. It opens a centered account dialog listing Personal and available organizations, with the active workspace marked from native state. Failed selections remain open. Account management opens the connection workspace. Keyboard focus remains inside the dialog and returns to the avatar on dismissal; motion respects reduced-motion preferences.

Organization setup accepts an address without a scheme; the native connection trims it and adds HTTPS before probing, and the form shows the normalized address. Connection and certificate verification appear on the account overview before login or invitation registration. Invitation registration signs in automatically. Password fields offer an accessible visibility toggle; creation, change and recovery require matching confirmation and at least eight characters. Operation feedback appears once, clears on editing or navigation, can be dismissed, and expires after six seconds; connection status and pending-write reconciliation remain visible.

The persistent Inbox and Run panel show execution questions, designated handlers, decision states and answers. File approval is separate from work information and requires reading the local tool parameters first. Recovery shows per-action reasons, the selected directory, its fingerprint and the remaining budget. Employee confirmation precedes either historical reconciliation or continuation. Unknown effects and stale baselines block continuation; expired ownership requires fresh explicit grant/claim and a new Run after cancelling the old one. None of these controls represents formal task acceptance.

`DeliveryPanel` shows a Run's explicit file sharing list, per-file type/description, deployment limits, verified uploaded hashes, selected submission artifacts, summary and target instructions. Upload and formal submission require human confirmation and remain separate actions. Standard file selection transfers only selected bytes; it never scans a directory or follows shared path metadata. Test reports render as escaped text, and downloads use a local `application/octet-stream` Blob without executing content. Git packages are explicitly selected JSON evidence in the documented format; automatic repository packaging and target application are not implemented in this phase. Task details and the original issuer's durable Inbox show the same immutable submission and downloadable evidence. Same-account permission refreshes hide stale content while preserving the mounted upload operation; identity changes clear sharing drafts. Visible Desktop acceptance remains user-owned.

`AcceptanceReview` requires the original issuer to confirm the displayed submission and evidence before accepting or rejecting. Rejection requires a reason and new requirements and explains whole-plan qualification invalidation. Task history shows accepted, rework, superseded and blocked outcomes separately; acceptance explicitly leaves target verification and final delivery outstanding. The employee Inbox retains a rework notice until the newer task version is approved, after which ordinary acceptance/delegation/claim controls apply.

`IntegrationPanel` separates prerequisite readiness, accepted required outputs, target observations and final delivery. It lists only the complete currently readable submission/hash set, requests a native directory dialog for verification and requires an explicit issuer checkbox before final confirmation. Native generations hide stale content. Actual target reads, permission and confirmation rules stay in Electron and the organization authority; the UI never supplies hashes as verification evidence. Visible acceptance remains user-owned.

## Codex task execution

The accepted-task execution form selects either the existing API backend or local Codex. Codex loads the safe Host model/effort catalog through `remote.session.modelCatalog`; no endpoint or key field is shown. The form retains the exact grant/create/open operation identities and expiry after failure. Execution summaries keep human assignee, device, revision, backend/model/effort, Run state, designated Inbox handler and delivery decisions separate. Existing fixed start/stop/resume/submission/acceptance/integration actions remain authoritative.

The employee-only native report presents known text and tool fields, authoritative native status and separate cleanup failures. A reviewed native recovery digest covers local journal events rather than filesystem contents. Unknown outcomes never enable an automatic resend. Callback answers require explicit continuation; native command decisions are consumed once for an identical fresh request under current authority. Unsupported file proposal comparisons require a fresh human decision. Account/organization/task identity changes retire local content and delayed responses. No page or browser automation is required for engineering validation.

Project and task conversations use the ordinary API/Codex model directory and execution capabilities. Backend successors retain the same organization selection and task controls; private messages follow the ordinary backend handoff behavior. Advanced finite Run execution retains its separate deployment limits.

`AccountSession` adapts the native authorized conversation to the existing Session Controller. `ui-session.registerMainSource` selects that binding in the existing `conversation` main destination. Organization mode uses the actual `ConversationPanel`, Chat assembler, Trajectory, message components, Lexical composer, model selector and planning/task controls. There is no organization conversation panel or alternate input implementation. Authorized planning events contribute an organization plan node to the normal Chat assembly. Task selection opens the current task's settings in the main task area.

The shared sidebar conversation menu offers Manage and Delete on hover or keyboard focus. Management persists rename and same-project Bot association; assignment Sessions keep their immutable assignment selector. Delete persists a tombstone before removing the private JSONL, hides the catalog entry and prevents assignment synchronization from recreating the deleted conversation. Account switches close management/creation dialogs, retire Session data and reject delayed results. Same-ID replacement retires old Controller references without affecting the replacement binding.

The native Inbox synchronizer reads all assignment pages for the current membership and materializes pending or accepted assignments without selecting the conversation or accepting, delegating, claiming or running the task. One durable Agent-authored message explains the authorized task goal, scope, acceptance and expected artifacts. The assigned node is selected in the common composer. A fresh project conversation can select another readable task node and persist that selection. Shared task/context facts are synchronized; private leader messages never enter the employee Session.

The common composer uses the ordinary Session prompt, attachment, slash-command and queue APIs, and the ordinary follow stream supplies live Assistant chunks. Native `attach` supplies a durable ordinary Session alias and retains account authorization; the Client contributes only task controls. Selecting a task supplies its authorized goal, scope and acceptance to that Agent. The task detail action opens this common conversation for execution. Assignment and other shared task changes retain their fixed organization permissions.

## Organization navigation and hierarchy

Switching to an organization fills the existing Projects, Bots and Recent browsers with that identity's authorized organization data. The global plus action directly creates an account-private conversation without a project; these conversations appear in Recent. Project-row creation retains its explicit project and optional Bot. Every enabled organization member can create a project from the Projects header; creation grants that member read/write access. Recent rows reopen their original private conversation. Bots are account-private, project-scoped configurations with a name, instructions and an ordinary API/Codex model selection. Their create/edit form reads the same model directory as personal conversations and saves through fixed native actions. A new conversation uses the Bot default; an explicit conversation selection takes precedence across reopen. Navigation reads every authorized project page independently of workspace search. A failed private catalog preserves the project rows and other successful catalogs; Recent reads conversations without a project independently of project enumeration. Identity changes clear conversation and task selections and restore the personal navigation registrations.

The Tasks browser uses the shared task-row presentation and lists readable roots. Selecting a row opens the same task canvas used by personal plans. Selecting a canvas node opens its scope, acceptance and current version in the right detail area, alongside assignment, editing and the action to execute in a common conversation. All pages of the selected authorized plan are read before drawing it; unreadable ancestors remain absent. To distribute work, choose a node, select a named eligible member, review the exact task version and confirm approval. Assignment supplies employee project and selected-task read/write access atomically. Ordinary members may assign to themselves and direct reports; administrators may assign any member, while project/task permissions remain mandatory.

The organization workspace's Hierarchy tab draws current reporting relationships. Administrators select a member, choose their direct supervisor (or a root), and explicitly save using the displayed version. The server refuses cycles and cross-organization supervisors and recomputes existing assignment eligibility. Chart visibility confers no project/task permission.

## Shared account presentation

Switching between personal and organization accounts selects a data partition within the existing sidebar and main destinations. Projects and Bots use the shared disclosure rows and contain their own conversations; expanding a group never creates a conversation. The group plus action opens the common creation dialog pattern, including optional Bot selection for a project. Recent rows reopen the original account-private conversation. Project actions open tasks in the main area; account dialogs retain membership, service and authorization administration.

Organization conversations occupy the existing `conversation` main key. They use the same Session binding, Chat/Trajectory assembly, message renderer and Lexical input as personal conversations. Enter sends an explicitly configured message, Shift+Enter keeps multiline input, and stop/error feedback remains visible outside the collapsed settings section. Tasks use the shared pan-and-zoom canvas and right-side detail presentation. The native organization adapters retain online permissions, identity generations and account-owned private history; sharing presentation never grants personal records organization ownership.
