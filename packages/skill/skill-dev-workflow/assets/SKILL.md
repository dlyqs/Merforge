# Personal task enhancement — managed method v4

Use this method when the effective planning policy enables automatic recognition or an explicit conversation choice. Planning grants no plan approval, execution ownership, tool permission, or continuous execution authorization.

1. Route the current accepted input before assessing it: use new_goal only for a new goal; clarification for an answer to a goal awaiting clarification; modify for a change to an existing goal with a plan; query for progress or details. For all three follow-up routes supply the exact existing goalId provided in the goal summaries. Never guess or use text equality to merge goals. Queries use simple and answer without proposing; an answer or progress question must not create another root. Understand the user's goal and assess its size. Call workflow_assess with the current mode revision and a concise explanation. Use simple for a bounded change with clear acceptance: continue ordinary assistance without creating any task or review. Use clarify when size, requirements, or feasibility are uncertain: ask the necessary questions and wait. Use infeasible when requirements cannot be met: explain missing conditions and alternatives; do not propose or execute the goal. Use complex only after material ambiguity is resolved and feasibility is established.
2. The assessment response provides the stable goalId. Keep it across clarification and modifications. balanced granularity uses hierarchical independently reviewable deliverables for task allocation (planningMode hierarchical). fine granularity uses a flat sequence of independently verifiable engineering phases for one local Agent (planningMode phases), each sized to fit a normal context window. In phases mode, use one required direct child of the root per phase, explicitly depend on the preceding phase task, place root acceptance verification in the final phase, and allow as many phases as the real work requires. Do not add intermediate groups to satisfy the five-child rule. Preserve phase identities and numbering when revising; split only a phase that execution evidence shows is too large, updating its dependencies and acceptance before execution. The following branching guidance applies only to hierarchical mode. For a feasible complex goal, state scope, acceptance criteria and deliverables. Summarize the overall goal into a short task name in the user's language before proposing: use that name as the root task's goal, aiming for at most 20 Chinese characters or 8 words. Do not copy the user's full request or enumerate subtasks in the name; retain the complete requirements in scope and acceptance. Give other nodes concise names too. Decompose into meaningful deliverable or workstream groups. Normally every node has at most 5 direct children. When more are needed, insert an intermediate level of meaningful groups and apply the same rule recursively; for example, place 10 subtasks under 2–3 groups instead of directly under the root. Do not invent filler work or unnecessary levels. Exceed 5 direct children only when grouping would obscure an inseparable set, and explain that exception in the parent's scope. Separate the parent-child tree (what the goal contains) from prerequisites (what must finish first). Siblings have no implicit execution order. Preserve explicit dependencies when grouping; never make a child depend on an ancestor that waits for it. Show independent branches and their join explicitly. Parent completion requires required children plus the parent's own acceptance evidence.
3. Allocate review stages in progression order. Place a parent no earlier than its required children, and a consumer no earlier than its prerequisites. Every task belongs to one stage; keep UUID identities stable when revising a plan. Use new UUIDs for new tasks, phases, and operations. Never reuse a removed task identity.
4. Call workflow_propose with a structured proposal. Do not put approval, completion claims, execution state, or authorization in the proposal. Use expectedRevision 0 for a new plan; use the exact current revision when editing. Keep the root taskId and child identities of the goal when modifying it; use the current exact revision. On an uncertain write retry the identical operationId and payload. Fix validation errors; never claim a rejected proposal was saved.
5. The returned pending-review plan is the only plan record. Tell the user to inspect and approve that revision. Stop before implementing the complex goal. Approval alone does not authorize execution; execution conversations and bounded continuation are separate actions. Never choose or start another task, create an execution conversation, or delegate yourself. After exact-version review, the user may authorize manual execution, all remaining phases, or an inclusive phase range, with optional fresh-conversation relay after a chosen phase batch. The application alone advances authorized phases and transfers execution ownership; each phase requires recorded acceptance evidence. A progress question, ordinary continue request, or plan approval never broadens authorization.

The structured definition contains planningMode (hierarchical or phases), taskId (root UUID), projectId and botId from the conversation, phases [{id, title}], and tasks [{id, parentTaskId, phaseId, goal, scope, acceptance, artifacts, cwd, dependsOn, required}]. The single root is required and has parentTaskId null. References stay inside the plan. Do not create cycles through either dependencies or required-child completion. A CSV example is: agreement → implementation and independent test-data preparation → integration; a separate root aggregates all necessary children and its own acceptance.

Follow existing tool approval, sandbox, and Bot Skill restrictions. A task review never replaces them. Do not read or rewrite a Markdown file as authoritative plan state. Do not use Codex task-management APIs, background scheduling, self-directed conversation relay, or absolute paths from the source author's machine. Markdown is a read-only export. The bundled upstream source documents the method's history; this managed method governs application behavior and replaces its file-plan and development-conversation procedures.
