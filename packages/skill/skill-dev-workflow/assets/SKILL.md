# Personal task enhancement — managed method v1

Use this method only while the user has enabled task enhancement for this conversation. Enabling it grants no plan approval, execution ownership, tool permission, or continuous execution authorization.

1. Understand the user's goal and assess its size. Call workflow_assess with the current mode revision and a concise explanation. Use simple for a bounded change with clear acceptance: continue ordinary assistance without creating any task or review. Use clarify when size, requirements, or feasibility are uncertain: ask the necessary questions and wait. Use infeasible when requirements cannot be met: explain missing conditions and alternatives; do not propose or execute the goal. Use complex only after material ambiguity is resolved and feasibility is established.
2. For a feasible complex goal, state scope, acceptance criteria and deliverables. Decompose it into independently identifiable tasks. Separate the parent-child tree (what the goal contains) from prerequisites (what must finish first). Siblings have no implicit execution order. Show independent branches and their join explicitly. Parent completion requires required children plus the parent's own acceptance evidence.
3. Allocate review stages in progression order. Place a parent no earlier than its required children, and a consumer no earlier than its prerequisites. Every task belongs to one stage; keep UUID identities stable when revising a plan. Use new UUIDs for new tasks, phases, and operations. Never reuse a removed task identity.
4. Call workflow_propose with a structured proposal. Do not put approval, completion claims, execution state, or authorization in the proposal. Use expectedRevision 0 for a new plan; use the exact current revision when editing. On an uncertain write retry the identical operationId and payload. Fix validation errors; never claim a rejected proposal was saved.
5. The returned pending-review plan is the only plan record. Tell the user to inspect and approve that revision. Stop before implementing the complex goal. Approval alone does not authorize execution; execution conversations and bounded continuation are separate actions. Never choose or start another task, create an execution conversation, or delegate automatically.

The structured definition contains taskId (root UUID), projectId and botId from the conversation, phases [{id, title}], and tasks [{id, parentTaskId, phaseId, goal, scope, acceptance, artifacts, cwd, dependsOn, required}]. The single root is required and has parentTaskId null. References stay inside the plan. Do not create cycles through either dependencies or required-child completion. A CSV example is: agreement → implementation and independent test-data preparation → integration; a separate root aggregates all necessary children and its own acceptance.

Follow existing tool approval, sandbox, and Bot Skill restrictions. A task review never replaces them. Do not read or rewrite a Markdown file as authoritative plan state. Do not use Codex task-management APIs, background scheduling, automatic conversation relay, or absolute paths from the source author's machine. Markdown is a read-only export. The bundled upstream source documents the method's history; this managed method governs application behavior and replaces its file-plan and development-conversation procedures.
