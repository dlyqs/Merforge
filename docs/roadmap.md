## 面向用户的完成标准

| 完成节点   | 用户可以完成的流程                                                                  | 不应误认为已完成的能力                          |
| ---------- | ----------------------------------------------------------------------------------- | ----------------------------------------------- |
| M3（当前） | 手工 JSON 计划 → 命令/最小 GUI 审阅执行 → 独立代码验收；异常恢复用 CLI              | 无菜单向导、无 LLM 自动规划、GUI 未完整覆盖恢复 |
| M3.1       | CLI 菜单或 GUI 表单各自完成现有人工工作流，包括核对重试                             | 仍是人工定义计划，不是聊天自动拆解              |
| M4         | 自然语言目标 → 追问 → 模块/任务/验收草案 → 用户审阅 → 真实执行 → 有界修复及独立验收 | 还没有企业领域访谈、改造评估和 ROI 专业能力     |
| M5         | 选择内置 Pack → 业务访谈/资料 → 可追溯的改造方案及实施任务                          | 方案已生成不等于流程已改造                      |
| M6         | 批准方案 → 实际实施/人工协作 → 工程、集成和业务验收                                 | 试点成功不等于自动上线生产或全企业转型          |
| M7–M8      | 比较实际效果；验证第二 Pack 与模型替换的复用性                                      | 不预设普遍收益，不提前建设空平台                |

两端使用同一服务、计划与权限语义。聊天是输入和协作入口，计划/审批/Attempt/证据才是工作状态事实。LLM 不直接授予自己执行权，独立验收不由聊天回复替代。产品演示继续强调持久执行和可核实成果，避免只有 Chat UI。

## 推进与维护约定

1. M1–M3 已完成各自既定范围，历史授权及验收留在原计划。M3.1 已按用户授权完成，实际状态与验收见详细计划；M4 仍需独立详细计划、审阅和授权。
2. 每个新 Milestone 开始前，用实际成果重新评估范围、依赖和可行性，创建详细执行计划并审阅。后续计划指定为当前入口后，更新本表和 overview 的导航。
3. 详细计划是 Phase 状态真源，本表仅记录里程碑状态和出口证据链接，不复制每次实现日志。
4. 模型集成前可用 Mock/Human 验证运行规则；M3 以后必须增加真实产物与失败样本，不能拿 Mock 通过率当业务成功率。
5. 原说明第 35 节的完整成果跨越 M5/M6，不压缩成下一阶段。原说明中 Phase 0 的业务契约随 M5 实际案例完成，运行时契约先在 M1/M2 稳定。
6. 评估数据从 M3 起增量积累，M7 做集中比较；验证每阶段都做，不推迟到 M7。
7. 时间估算需结合前一里程碑的实际速度与外部条件；当前以验收出口规划，不填写虚构工期、收益或完成百分比。
