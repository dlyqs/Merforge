# M4：对话规划、多执行器与执行验证闭环

## 文档地位

2026-09-15 补充产品交付合同；不是已实现说明，也不是自动执行授权。里程碑状态以 [roadmap](roadmap.md) 为准。进入条件为 M3.1 双端人工操作闭环完成；临近实施时基于实际代码拆分详细 Phase，本文不维护第二份阶段状态。

M4 的完成必须同时证明 LLM 规划能力、CLI/GUI 交互和真实执行验证。仅完成 Planner API 或生成 JSON，不足以完成 M4。

## 两端共享的用户流程

选择仓库/上下文 → 自然语言描述目标 → LLM 追问并澄清 → 生成模块、阶段与任务草案 → 展示依赖、范围、验收及风险 → 用户修改/确认版本 → 选择执行器与运行边界 → 显式启动 → 跟踪真实结果 → 有界修复或人工处理 → 独立验收 → 查看最终 diff/交付报告。

- CLI 在 M3.1 菜单中增加自然语言新建、澄清问答、计划草案审阅与修订、进度/异常处理。日常流程不用手写 JSON、内部 ID、hash；保留可脚本化命令。
- GUI 以类似 AI Chat 的对话作为主要新建入口，配合结构化计划、任务、进度、审批和证据视图。用户可以聊天修订草案，或直接编辑结构化字段；不能只显示聊天消息而缺少工作状态。
- 对话历史、规划草案、批准版本、实际运行分别持久化并关联。刷新/重启可继续澄清或查看工作状态，不能靠模型上下文记忆恢复调度。
- 对话提出的“继续/停止/重试”是待校验的操作意图，必须映射到与菜单相同的版本化 Runtime 命令。生成计划或一条普通聊天回复本身不授予执行权限；具体授权动作需明确绑定范围和版本。
- 菜单、聊天和 GUI 的运行状态来自同一服务；多端过期状态必须拒绝，聊天文本不能覆盖事实记录。对运行中 Executor 的实时 steer/send 不作为默认能力；有需求时必须单独验证适配器支持及边界。

## 核心能力及验收出口

| 能力         | 必须交付                                                                            | 必须拒绝或保留不确定性                                                                |
| ------------ | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 上下文与澄清 | 基于操作者选定的仓库/资料理解目标，记录约束、问题、回答及假设                       | 缺必要信息时等待用户；不扫描未授权目录、不虚构仓库事实                                |
| LLM Planner  | 生成结构化、可修订的目标/模块/阶段/任务，附输入、输出、依赖、执行器需求、范围、验收 | 输出不合法、循环依赖、无验收或能力不足不能直接派发                                    |
| 模块拆分     | 展示职责与文件/接口边界，并能追溯到任务和需求                                       | 模块可先作为规划分组；是否新增持久化实体由实际语义决定，不先造空框架                  |
| 草案审阅     | 展示 LLM 建议与原始要求的对应、版本差异、影响范围及风险；用户可拒绝或修改           | 聊天修订不修改正在执行的冻结定义；范围/验收变更创建需审阅的新计划并保留关联           |
| 执行器能力   | Codex、Claude Code、Human 的真实能力声明、选择/匹配、不可用诊断                     | 不可用不静默退回 Mock；Human 示例 summary.v1 不冒充代码/业务验收                      |
| 依赖与边界   | 校验依赖，按有效顺序调度，支持长目标阶段停止与恢复                                  | 并行仅在工作区隔离、产物合并和调度回归通过后开放；不为展示效果绕过串行保障            |
| 修复与验证   | 独立 FAIL 后形成可追溯的修复尝试/任务，再执行原验收；记录次数、耗时和原因           | 只有明确预授权且在范围/预算内才自动修复；未授权、超限、重复失败则停止，不降低验收标准 |
| 最终交付     | 两端均能查看实际文件变更、验收报告、未完成项、操作记录和可得用量                    | 对话声称完成不代表 PASS；不自动合并、推送或部署                                       |

修复策略须在首次启动前让用户选择手动处理或有界自动修复，并明确次数、时间/用量限制及停止条件。缺失成本/用量字段记 unavailable，不能视为没有消耗。验收定义即使由 LLM 起草，也须在执行前审阅并冻结；检查基准与被执行 Agent 的写入范围分离。M3 当前 plan.v2 为全代码计划，M4 的混合执行器与新验证能力必须先落契约和兼容迁移，不能只在 UI 加选项。

Planner 优先复用成熟 Agent/模型适配能力；技术选择在真实协议探针后确定，不默认建设新的通用 Agent Loop。Planner、Executor、Verifier 保持分工，角色不等于必须启动三个并行 Agent 进程。同会话 resume 仍按各适配器实测声明，不是聊天历史持久化的同义词。

## M4 最终验收

1. 用户从空白目标开始，分别通过 CLI 菜单/问答和 GUI 聊天提出一个多模块代码目标；不借助外部脚本编写计划或手改数据库。
2. 真实 LLM 能澄清关键歧义、生成模块/任务及验收草案；修改要求后有可审阅的新版本，未批准不得执行。
3. 真实代码样例完成规划、审阅、执行、独立验收；至少证明 Codex 与 Claude Code 的实际适配能力，并有 Human 等待/提交场景。凭证或能力缺失应保留未完成项，不能用替身完成里程碑。
4. 有真实负例证明 FAIL、限定范围的修复与重验，以及超出修复额度后停止；有到界停止、重启保持边界和显式恢复证据。
5. 取消、重复发送、过期审批、LLM 错误输出、网络/模型错误和上下文缺失均有明确状态。不能用聊天 UI 动效代替完成证据。
6. 两端操作分别验收；CLI 用菜单/问答输入回归，GUI 用输入/操作层与 API 集成、类型/构建检查。助手不使用浏览器，用户视觉检查可选并单列。真实模型证据与替身回归分开记录。

M4 结束时同步实际命令、页面路径与使用说明，才可对外声明“聊目标到执行验证”的完整产品流程。M5 将企业领域分析接入此流程；其需求见 [AI Transformation Pack](ai-transformation-pack-scope.md)。
